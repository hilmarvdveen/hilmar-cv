# i18n: how a page gets its language, and how to prove every page has it

The site is bilingual (Dutch default, English second) on next-intl 4 with the
App Router. This document records how the locale reaches server and client
components, the incident of 1 September 2026 where English visitors saw Dutch,
the rules that follow from it, and the sweep that proves every route renders
in its own language.

## How the locale reaches a component

Two paths, and they must agree:

1. **Server components** (`useTranslations` or `getTranslations` in a file
   without `"use client"`) get their locale from the request config in
   `src/i18n/request.ts`. next-intl calls that config once per request with
   `requestLocale`, a promise of the `[locale]` segment the middleware
   matched, and with `locale` only when a caller passed one explicitly
   (`getTranslations({ locale })`). The config resolves the value against
   `routing.locales` and falls back to `routing.defaultLocale` for unknown
   segments.
2. **Client components** get their locale and messages from
   `NextIntlClientProvider` in `src/app/[locale]/layout.tsx`, which passes the
   segment's locale and `getMessages({ locale })` explicitly.

`next.config.ts` points the next-intl plugin at `./src/i18n/request.ts`. There
is exactly one request config. Do not add another (a root
`next-intl.config.ts` once duplicated it and was the active one).

## The incident: English visitors saw Dutch

**Symptom.** On `/en` the hero and the buttons were English but the results
strip, the case, the method, the standards, the hiring FAQ and the close were
Dutch. Nothing was missing from `en.json`.

**Cause.** The request config destructured `{ locale }` and fell back to
`"nl"` when it was undefined. next-intl 4 removed that parameter in favour of
`requestLocale`, so every server component rendered Dutch. Client components
were fine because the layout hands the provider the locale explicitly. The
mix looked like missing translations, and it was a resolution bug.

**Why it went unnoticed.** Every component test mocks `useTranslations`, so
no test renders a page with real messages, and the request config had no test
at all. The homepage was reviewed in Dutch first.

**Fix.** `request.ts` reads `locale ?? (await requestLocale)`, validates it
against `routing.locales`, and is covered by `request.test.ts`. The catch-all
route `src/app/[locale]/[...rest]/page.tsx` calls `notFound()` so unknown
URLs inside a locale render the translated `not-found.tsx` with the layout,
instead of Next's bare English 404.

## Rules

- **One request config**, `src/i18n/request.ts`, resolved from
  `requestLocale` with an explicit `locale` taking precedence. Never fall back
  silently in a way a test cannot see.
- **Message files are the only copy source.** No literal sentence in a
  component, and that includes `aria-label`, `placeholder`, `alt` and `title`
  attributes. The drawer's "Open menu", "Close menu" and "Language" and the
  contact page's "Contact information" were the last ones.
- **Every key exists in both files** with the same type and array length.
  `src/i18n/messages.test.ts` enforces this in the normal test run.
- **A `defaultValue` in a `t()` call is not a translation.** It hides a missing
  key in one language. Use it only for values that are legitimately the same
  in both languages (a company name).
- **Unknown routes render the localized 404.** Keep the `[...rest]` catch-all.
  Known limitation: because the app has no root `app/layout.tsx` above
  `[locale]`, Next serves a 404 as its error shell (`<html id="__next_error__">`
  with an empty body) and the translated page, header and footer render on
  the client from the flight payload. The status is 404 and the content is
  right once hydrated. A crawler sees the status, which is what matters for a
  404. The crawl script therefore checks the 404 by its localized title in the
  response, not by `<html lang>`.
- **Blog posts are English-only content by design.** Their code samples and
  the ReactFlow diagram's built-in English accessibility text show up in a
  Dutch-page scan. That is expected.

## The sweep

Two checks, one static and one rendered.

### Static: key parity

`pnpm test` runs `src/i18n/messages.test.ts`: same namespaces, same leaf keys,
same value types and array lengths in `en.json` and `nl.json`.

### Rendered: crawl both locales

```bash
pnpm build && pnpm start -p 3123
pnpm check:locales http://localhost:3123
```

`scripts/crawl-locales.mjs` fetches every route in both locales and flags a
page when:

- the status is not 200 (the deliberate unknown route must return 404 and
  carry the localized `notFound.title` in its response),
- `<html lang>` does not equal the locale,
- a message key leaks into the visible text (`home.hero.title` style),
- a 12-word window of visible text contains three or more common words of the
  other language.

Known false positives: the blog posts (code samples, the diagram's
"space to select a node" text). Everything else is a finding. Run it against
the production build, not the dev server: the dev server keeps a lock in
`.next/dev`, refuses a second instance, and does not reload `next.config.ts`.

### What the first sweep found (1 September 2026)

- The request config bug above (every server component on `/en`).
- The bare Next 404 in both languages.
- `services.cta.description` missing in `en.json`.
- Hardcoded `aria-label`s in the header drawer, the contact hero and the
  breadcrumb, plus a literal "Language" heading in the drawer.
- `footer.about.title` said "Senior Full-Stack Engineer" in both files
  against the frontend positioning.
- Dead namespaces left over from the old homepage (`home.usp`, `home.about`,
  `home.tech`, `home.projects`, `home.cta` in part) and a stale
  `common.home.summary` ("over 7 years"). None renders. Listed as cleanup.
